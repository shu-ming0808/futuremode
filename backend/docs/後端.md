# OpeningGuard AI：後端需求與技術決策

> 本文件只描述後端。前端由另一位組員負責，不列入本人的實作範圍。

## 1. 專案目標

OpeningGuard AI 是提供券商內部團隊使用的開盤容量決策工具。系統針對「下單請求」模擬 09:00～09:05 的流量尖峰，比較固定容量、反應式擴容與提前預熱，回答：明日開盤前應準備多少 worker，才能在服務目標內承受預期風險。

Demo 所說的成功是：

```text
券商後端完成驗證，交易閘道回傳「委託已接受」
```

這不代表訂單已成交，也不預測成交價格。

## 2. 為什麼一定要使用 Agent

輸入同時包含兩類資料：

- 結構化資料：版本化情境中的流量、worker、Database 與交易閘道容量。
- 非結構化資料：營運人員輸入的自然語言備註，例如「海外市場劇烈震盪」或「DB pool 幾乎沒有空閒連線」。

OpenAI Agent 負責閱讀營運備註，從既有風險目錄中選擇最多三個 `risk_id`，並為每個風險選擇 `low`、`medium`、`high` 或 `uncertain`。一般規則程式再依 `risk_id + severity` 套用已審核的倍率、執行模擬並產生容量建議。

Agent 的邊界：

- 只能選擇風險目錄中已存在的 `risk_id`，以及固定列舉的 `severity`。
- 不得自行產生 RPS、風險倍率、worker 數或其他模擬參數。
- 不得修改版本化情境。
- 不得宣稱委託已成交。
- Agent 結果需保留模型名稱、選到的 `risk_id`、理由與是否為真正 LLM 結果，方便稽核。
- 沒有 `OPENAI_API_KEY` 時 Agent 路徑直接失敗；離線 demo 走 `AGENT_PROVIDER=mock`，且必須標示不是 Agent Demo 或 Agent 評測證據。

### 已確認：OpenAI 多評審的事件嚴重度判斷

只使用一組 OpenAI API 憑證也能完成多評審流程：後端對同一份營運備註發出三個分開的 Responses API 請求，讓三個 judge 各自判斷事件嚴重度。若三次都使用同一模型，應稱為「同模型多評審」或「multi-agent voting」，不可宣稱是三個彼此獨立的 LLM。

### 已確認：人工標記 few-shot 與 held-out 評測

Agent 分級採用 rubric-based few-shot classification：專案先建立人工標記案例，再把其中一份只作為 prompt demonstrations，協助模型理解 low／medium／high 的容量影響界線。另一份案例完全不放進 prompt，只用於最後評測，避免資料洩漏。

```text
prompt_examples.json：12 筆人工標記示範，只供 prompt 使用
eval_cases.json：15 筆 held-out 案例，只供評測使用
```

程式會驗證兩份資料沒有相同的營運備註。Prompt examples、rubric、風險目錄與 structured scenario 是固定輸入；每次待判斷的 `target_operation_note` 放在最後。模型的輸出仍由 strict function tool schema 限制，不使用自由文字解析，也不讓模型自行產生倍率或容量數字。

人工標記是評測 ground truth；三位 judge 的多數票只用於執行時穩定性，不能取代 held-out accuracy、macro-F1、confusion matrix 與 weighted kappa。

建議不要直接讓模型輸出任意分數，而是將低／中／高拆成兩個有順序的二元判斷：

```text
is_at_least_medium：0 或 1
is_high：0 或 1
限制：is_high = 1 時，is_at_least_medium 必須等於 1
```

三位 judge 的彙整規則：

```text
high_votes >= 2                    → high
否則 medium_or_higher_votes >= 2  → medium
否則                               → low
```

每次輸出都必須使用固定 JSON Schema，包含 `risk_id`、兩個 0/1 判斷、引用的原始備註片段與簡短理由。如果三位 judge 嚴重分歧、缺乏證據或輸入超出風險目錄，回傳 `uncertain` 並要求人工覆核。

若三位 judge 分別投出 `low`、`medium`、`high`，或其他情況導致沒有多數共識，採用以下正式規則：

```text
正式 Agent 結果：uncertain
容量風險預覽：套用版本化 JSON 中既有的 high 參數
最終容量決策：requires_human_review = true
自動核准：false
```

這裡的 `high` 只記錄在 `simulation_assumption`，不可覆寫 `agent_severity`。系統可以顯示最壞情境下的容量需求，但不得把保守預覽冒充 Agent 已確定的高風險判斷，也不得自動部署或擴容。

即使加入嚴重度判斷，Agent 仍不得輸出倍率或容量數字。`low`、`medium`、`high` 對應的倍率必須預先寫在版本化 JSON，由一般程式套用。此項已確認為正式安全邊界。

`severity` 明確定義為事件發生後對系統容量的影響程度，不是事件發生機率。三位 judge 的票數只表示判斷共識；同模型輸出具有相關性，不能視為三個獨立統計樣本。

同一模型的三次輸出具有相關性，不能把票數當成三個獨立統計樣本，也不能用普通二項分布信賴區間宣稱模型可靠。可靠度必須另外使用人工標註測試集，報告 confusion matrix、macro-F1 與 ordinal weighted kappa。

## 3. 系統流程

```text
自然語言營運備註
        ↓
三個 OpenAI judge 選擇既有 risk_id + severity
        ↓
後端載入版本化固定情境參數
        ↓
依 risk_id 套用已核准的風險倍率
        ↓
Monte Carlo Queue 模擬與容量搜尋
        ↓
比較固定容量／反應式擴容／提前預熱
        ↓
輸出建議、統計證據與警告，等待人工確認
```

Agent 是「風險分類與工具調用層」，數值計算仍由可重現的 Python 模擬器完成。這能證明 AI 是必要組件，同時避免 LLM 幻覺直接控制容量。

## 4. MVP 排隊模型

主要事故設定為：

```text
Worker 容量不足 → FIFO Queue 累積 → 回應超過 2 秒 → 客戶端重試 → 流量再被放大
```

次要限制為：

```text
Database／交易閘道有硬上限 → 一直增加 worker 也無法繼續提高吞吐量
```

模擬採用單一 FIFO 下單 Queue，時間範圍 300 秒，以 100 ms cohort 更新狀態。這是黑客松 MVP 的快速近似，不宣稱是券商正式撮合系統。

`合成下單到達率 → FIFO Queue → API Workers → Database 硬上限 → 交易閘道硬上限` 描述的是每筆下單請求在模擬中的容量路徑，不是三種策略的比較圖。它的用途是保留端到端瓶頸：實際可處理量取 worker、Database、交易閘道三者中的最小值，所以增加 worker 不一定能解決下游飽和。固定容量、反應式 autoscaling、預測式預熱才是沿用同一條容量路徑進行比較的三種策略。

每個請求的主要階段：

1. 請求格式與商業規則驗證。
2. 等待可用 worker。
3. 模擬 Database 延遲與容量限制。
4. 模擬交易閘道延遲與容量限制。
5. 回傳「委託已接受」或逾時／失敗。

## 5. 容量公式

每台 worker 的有效處理能力不是任意填入，而由下式推導：

```text
有效 RPS = concurrency slots ÷ 平均服務時間（秒）× efficiency
```

目前固定情境的示範值：

```text
20 ÷ 0.2 × 0.8 = 80 RPS／worker
```

- `concurrency slots = 20`：同一個 worker 同時可處理的請求數。
- `平均服務時間 = 0.2 秒`：驗證、Database 與交易閘道的平均總處理時間。
- `efficiency = 0.8`：考量排程、序列化、連線等待與其他額外成本後的效率折減。

這組數字目前是可替換的 Demo 假設，不是公開資料證明的券商真實容量。公開市場資料可協助描述「下單到達型態」，但服務時間與效率必須由本機或實際環境壓測校準。

## 6. 流量與統計假設

開盤下單量使用「盤初衰減曲線＋日間強度衝擊＋短期群聚」產生合成 RPS，而非只跑一條固定曲線。

- 固定 seed：確保 Demo 可重現。
- 多個 Monte Carlo run：估計不同交易日可能產生的結果分布。
- Demo 快速結果固定使用 500 個模擬開盤日；正式統計證據固定使用 2,000 個模擬開盤日。
- 正式樣本數在查看結果前先決定，避免看到結果後才調整次數。
- 混合 Poisson／Cox 類型衝擊：表達不同日期的整體強弱差異。
- AR(1) 型短期擾動：表達尖峰會在相鄰時間區段群聚。
- Hawkes process：只列為未來優化，用於事件級下單資料充足時描述自激與群聚。
- 開盤 Monte Carlo 不做 burn-in；09:00 的初始尖峰正是研究目標，不得丟棄。

不能宣稱公開論文已證明本專案的券商下單資料符合 Hawkes 分布。正確說法是：金融訂單事件的群聚研究提供模型設計依據，實際適配仍需用資料比較 Poisson、Negative Binomial、Cox 與 Hawkes。

## 7. 固定版本情境

後端只接受情境 ID（API 欄位名為 `scenario`），再載入 Git 管理的固定 JSON 情境。目前不接受呼叫端自行傳入 RPS、倍率、P50、P90、P99 或 market features。

至少保留三種情境：

1. 正常流量：固定容量也能符合目標。
2. 高壓流量：固定容量堵塞，提前預熱方案通過。
3. 下游瓶頸：Database／交易閘道達到上限，增加 worker 仍無效。

每次結果需回傳 `scenario_version`、`simulator_version`、random seed 與推導後的每 worker 有效 RPS，確保結果可追溯。

## 8. 三種容量策略

### 固定容量

全程使用相同 worker 數，作為比較基準。

### 反應式 autoscaling

Queue 超過門檻後才擴容，並計入偵測與 worker 啟動時間。因此它可能來不及處理開盤瞬間尖峰。

### 預測式預熱

根據 Agent 選出的風險，在開盤前配置既有候選方案。目的是在流量進入前取得容量，不是讓 Agent 即時任意建立資源。

## 9. 容量搜尋與服務目標

目前搜尋固定候選 worker 數，並選出符合服務目標且 worker-minute 成本最低的方案。

```text
P95 延遲 < 2 秒
逾時率 < 0.1%
堵塞機率的 Wilson 95% 信賴區間上界 < 5%
Database／交易閘道不超過安全利用率
```

若沒有安全方案，後端必須回傳原因及警告，不可硬選不安全的方案。

堵塞機率不能只用 Monte Carlo 點估計判定。例如觀察到 4%，但 Wilson 95% 信賴區間為約 2.6%～6.1%，因為上界仍超過 5%，所以不通過。只有信賴區間上界也低於 5% 才能正式宣稱符合門檻。本版程式已改用信賴區間上界判定，相關 regression test 已通過。

### 最大穩定吞吐量的正式定義

對某個目標 RPS 進行壓測時，必須同時符合以下條件才算「穩定」：

- 至少 99.9% 的有效下單請求在 2 秒內收到「委託已接受」。
- HTTP 5xx、連線錯誤與逾時合計低於 0.1%。
- 停止送入新請求後，FIFO Queue 能在 2 秒內清空。
- P95 延遲低於 2 秒，並作為輔助比較圖表。

HTTP 4xx 的格式或商業規則驗證失敗應另外統計，不可混入伺服器容量失敗。原先「測試期間完成比例大於等於 90%」的門檻只適合觀察短期積壓，對券商下單過於寬鬆，因此不再作為正式穩定容量標準。

主要輸出：

- congestion probability 與 95% Wilson interval。
- P95 latency。
- timeout rate。
- maximum Queue length。
- Database 與交易閘道 peak utilization。
- worker-minute 成本。
- 建議策略及無解原因。

## 10. FastAPI 串接端口

前後端在同一台電腦執行：

```text
後端：http://127.0.0.1:8000
GET  /api/health
POST /api/assessments
POST /api/mock-orders
```

- `/api/assessments`：接收 `scenario` 與自然語言營運備註，回傳 Agent 判斷和三種策略結果。
- `/api/mock-orders`：只供本機容量校準，永遠不會送出真實交易。
- CORS 預設只允許本機開發端口；正式環境需另行設定。

## 11. UUID 與重試語意

App 應在第一次送單前產生 UUID，同一筆訂單的所有重試沿用相同 UUID。若等到後端收到後才產生，就無法辨識兩次 HTTP 請求是否為同一筆交易意圖。

MVP 目前不建置 SQLite 或正式 Database，因此只能模擬 idempotency 語意，不能宣稱已做到跨程序、重啟後仍可靠的防重複下單。未來串接真實資料庫時，UUID 應設唯一索引並搭配訂單狀態機。

## 12. 本機 mock 校準流程

校準 API 模擬三段工作：

- 請求驗證延遲。
- Database 延遲。
- 交易閘道延遲。

要量測：

- 平均服務時間。
- P95 服務時間。
- 最大穩定吞吐量。
- concurrency 增加後的效率衰減。

其中「最大穩定吞吐量」採用第 9 節的正式定義，而不是只看平均 throughput 或 P95。測試結束後必須保留 2 秒 drain period，確認 Queue 能清空，再依每一筆請求的完成時間判斷是否在 SLO 內。

校準結果只寫入：

```text
backend/calibration_results/latest.json
```

結果不得自動覆寫版本化情境 JSON，也不得讓 Agent 改參數。若要採用新量測值，必須人工審查後建立新的 `scenario_version`。

### 已確認的測試模式

- 快速 Demo：每個設定約 3 秒、1 次，目的是快速展示流程，不作正式統計證據。
- 正式證據：先進行 5 秒 warm-up，再正式量測每個設定約 30 秒、重複 5 次，報告平均值、P95、重複間變異與 bootstrap 95% confidence interval。
- 停止送入新請求後保留 2 秒 drain-out，確認 Queue 是否能在服務目標內清空；每筆請求的完整延遲仍需列入統計。
- 5 秒 warm-up 只用於本機 HTTP 壓測，避免 Python 與 HTTP connection pool 的首次啟動成本干擾穩態容量量測。
- 開盤 Monte Carlo 不使用 burn-in，完整保留 09:00～09:05，避免刪除研究的主要尖峰。
- 正式證據模式預先產生結果與圖表，不在 Demo 現場即時執行。

2026-09-04 已執行 quick profile 並重產 `latest.json`：探索性最大穩定 target RPS 為 120；160 RPS 時 P95 約 2031 ms、SLO 內接受率約 90.6%，且 Queue 未在 2 秒 drain-out 內排空。由於 quick profile 僅單次、每組 3 秒，結果標示 `evidence_grade=false`，不能當成正式容量證據。正式 evidence profile 尚未執行。

## 13. Notebook 與展示分工

統計流程放在 `backend/notebooks/statistical_analysis.ipynb`，每個 code block 前都需要 Markdown 簡述其目的。

Notebook 用於提供可信度證據：

- 合成開盤流量圖。
- 多日 peak RPS 分布。
- 三種策略的 Monte Carlo 比較。
- 堵塞機率 confidence interval。
- P95 與 2 秒 SLO 比較。
- 成本與成功率比較。
- 流量倍率 × worker 數的 sensitivity heatmap。
- Database／交易閘道硬上限。
- 本機壓測的 throughput、P95 與 efficiency curve。

PPT 負責解釋問題、方法、Agent 必要性與商業價值；預錄 Demo 只展示實際操作流程。參數掃描與大量統計圖放在證據頁，不塞進主 Demo 流程。

## 14. 目前限制與後續工作

- 真正 OpenAI Agent 呼叫與 15 筆 held-out 人工標註案例仍需使用 API key 正式評測；few-shot 與 test split 已分離，但尚未取得模型分數。
- 目前為 100 ms cohort 近似，不是逐事件的正式離散事件引擎。
- 尚未串接真實 Database、交易閘道或券商營運資料。
- 尚未建立持久化 idempotency store 與訂單狀態機。
- 尚未完成 Poisson、Negative Binomial、Cox、Hawkes 的實證適配比較。
- 尚未加入正式環境所需的驗證、授權、rate limiting、logging、metrics、tracing 與部署設定。
- 正式 evidence 校準的重複執行與 bootstrap confidence interval 已完成程式碼，但尚未跑完數十分鐘的正式測試；目前只有 quick 探索結果。
- regression tests 已執行 9 項並全數通過；包含 few-shot rubric 與 held-out split 檢查，仍缺更完整的整合、效能 regression baseline 與 CI。
- `calibration_results/latest.json` 已使用新版 quick 規則重產，但不是 evidence-grade 結果。
- Notebook 已使用 500-run Demo profile 與 Wilson 上界規則重新產生；2,000-run 三策略基準已驗證可執行，但尚未嵌入完整 evidence 圖表。
- 2,000-run 三策略比較在本機耗時 579.37 秒；完整容量搜尋還會測試 6 個 worker 候選，不適合作為同步 Demo API 工作。

## 16. 本版完成與驗證狀態

- 容量方案正式通過條件改為：`congestion_probability_ci95.upper < 0.05`。
- Agent 輸出由只有 `risk_id` 擴充為 `risk_id + severity`。
- `severity` 只能是 `low`、`medium`、`high` 或 `uncertain`。
- 使用三個 OpenAI judge 進行有序二元投票；同模型時不得宣稱為三個獨立 LLM。
