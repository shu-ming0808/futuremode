# 真實事故候選資料：人工標註說明

## 這份資料是什麼

`openingguard/data/manual_label_candidates.json` 收錄 14 筆由公開來源整理的券商、交易平台與相鄰市場基礎設施事故。AI 先依容量影響 rubric 草擬每筆 `risk_id`、低／中／高嚴重度、原文證據及判斷理由，再由使用者逐筆覆核並核准第一版。核准後的分布為低 2 筆、中 6 筆、高 6 筆。

每筆都使用 `reviewer: "user"` 與 `review_status: "user_approved_first_version"`，表示這是使用者核准的單人標註第一版。本階段不要求第二位標註者；AI 草稿本身不算獨立人工標註者，因此不能宣稱有人工標註者間一致性。

這批資料目前不會自動加入 `prompt_examples.json`，也不能直接宣稱是模型訓練集或準確率證據。下一步要先固定資料切分：選為 few-shot 的事故只能放進 prompt，選為 held-out 的事故只能用於最終評測，避免資料洩漏。

## 你需要填哪些欄位

每一筆只修改 `annotation`：

```json
{
  "risk_matches": [
    {
      "risk_id": "從 valid_risk_ids 選擇，總共最多三個",
      "is_at_least_medium": 0,
      "is_high": 0,
      "matched_input_text": "從 annotation_text_zh 原文複製一段證據",
      "reason": "一到兩句容量影響理由"
    }
  ],
  "no_confident_match": false,
  "reviewer": "user",
  "status": "fully_labeled_user_approved_first_version",
  "review_status": "user_approved_first_version"
}
```

若沒有任何可支持的風險，將 `risk_matches` 留空並把 `no_confident_match` 設為 `true`。每個風險可有不同 severity，所以兩個 0/1 欄位必須放在各自的 `risk_matches` 內。

嚴重度是對系統容量與服務可用性的影響，不是公司損失金額，也不是事件再次發生的機率：

| severity | is_at_least_medium | is_high | 判斷原則 |
|---|---:|---:|---|
| low | 0 | 0 | 影響有限，沒有明顯 Queue、逾時或核心下單功能中斷 |
| medium | 1 | 0 | 已明顯增加等待或影響部分核心功能，但沒有足夠證據顯示大規模中斷或 SLO 違反 |
| high | 1 | 1 | 已出現核心下單中斷、大量 pending／重複委託、下游飽和或明顯 SLO 違反 |

若風險目錄沒有適合的類別，使用 `unknown_unquantified_risk`，不要硬塞到最像但不正確的 `risk_id`。`real_013` 與 `real_014` 特別保留作 out-of-domain 測試，合理答案可能就是 `unknown_unquantified_risk`。

## 金額欄位如何閱讀

- `company_direct_loss`：來源明確稱為公司實際或直接損失。
- `company_recognized_aggregate_loss`：公司財報認列的整體損失，可能包含多個部分。
- `customer_compensation`／`customer_compensation_or_restitution`：付給客戶的補償或監管命令的 restitution。
- `regulatory_fine`：主管機關罰款，不是事故本身造成的交易損失。
- `erroneous_trade_notional`／`executed_erroneous_orders`：錯帳或錯誤委託的名目金額，不等於最後損失。
- `null`：公開來源沒有可靠數字，不代表損失為零。

金額可用於商業衝擊敘述與案例排序，但不可交給 Agent 自動換算 RPS、倍率或 worker 數。

## 本版採用的人工標註流程

1. AI 根據 `annotation_text_zh` 與來源資料提出第一版標籤草稿。
2. 使用者逐筆覆核風險、嚴重度、原文證據及理由，必要時修改後核准。
3. 若來源不足以判斷嚴重度，記錄缺少的證據；風險目錄沒有合適項目時使用 `unknown_unquantified_risk`，不要硬套錯誤類別。
4. 核准資料標示 `reviewer=user` 與 `review_status=user_approved_first_version`。
5. 最後才切分 few-shot 與 held-out，禁止同一事故的近似改寫同時出現在兩邊。

第二位標註者不是第一版必要條件。若未來要在論文或正式報告中宣稱這批資料是高可信度 gold labels，可再增加盲標、分歧裁決與標註者間一致性分析。

## 給 LLM 評分時使用的 Prompt

人工 gold label 完成後，可用下列文字作為評測任務說明。正式程式仍會以 strict function calling 限制輸出格式：

```text
你是券商下單系統的容量風險分類員。請只根據 target_operation_note 的原文證據，從提供的固定 risk catalog 選擇最多三個 risk_id。

對每個 risk_id 分別回答兩個有序二元問題：
1. is_at_least_medium：事件是否已明顯增加 Queue、等待或核心資源壓力？只能填 0 或 1。
2. is_high：是否有明確證據顯示核心下單中斷、大量 pending／重複委託、下游飽和或 SLO 違反？只能填 0 或 1。

is_high=1 時，is_at_least_medium 必須等於 1。severity 衡量容量與服務影響，不是金錢損失或發生機率。不得輸出或推測 RPS、倍率、worker 數、損失金額。matched_input_text 必須逐字複製自 target_operation_note。證據不足或目錄無適合項目時，回傳 no_confident_match=true 或選擇 unknown_unquantified_risk，不要猜測。
```

## 為什麼不直接自動爬完就當標籤

搜尋與 NLP 可以協助找候選文章、抽取日期、公司、故障現象與金額，但三個問題仍需人工判斷：同一事故可能被多家媒體重複報導；「損失」可能其實是罰款或錯帳名目金額；事故描述也不一定能對應本專案的固定容量風險目錄。因此本版採用半自動流程：搜尋召回候選，人工驗證來源與標註，LLM 最後接受 held-out 測試。
